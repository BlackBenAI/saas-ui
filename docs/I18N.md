# Documentation languages

SaaS-UI uses English as the source language for code, identifiers, and documentation. The
hosted edition (`saas-uiBBA/`) additionally ships its interface in **English, French, and
Spanish** and treats every new user-facing string as translatable.

This page defines how the same rule applies to documentation and the wiki.

## Contract

- **English is the source.** Write or update the English page first.
- **Every translated docs tree must stay complete.** A page added to `en/` must have a matching
  page in `fr/` and `es/`, or be explicitly marked as not yet translated.
- **No mixed-language pages.** Do not translate half a page in place. Either translate the whole
  page or leave it in English and link to it as English.
- **Code blocks, commands, file paths, API names, and product names are not translated.**
- **Screenshots may be shared across languages** when the UI language does not change the
  message. Otherwise capture a localized screenshot in the matching language folder.
- **Legal text is not machine-translated.** Keep the reviewed source language and translate only
  navigation and section titles until a reviewed translation exists.

## Recommended structure

For a documentation site, use locale roots with English as the fallback:

```text
docs/
  site/
    .vitepress/config.ts
    index.md            # English
    guide/
    fr/
      index.md
      guide/
    es/
      index.md
      guide/
```

VitePress is the recommended generator because the editor already uses Vite. It provides a
native language selector, per-locale sidebars, and URL-based language routing:

```ts
// docs/site/.vitepress/config.ts
export default defineConfig({
  locales: {
    root: { label: "English", lang: "en" },
    fr: { label: "Français", lang: "fr", link: "/fr/" },
    es: { label: "Español", lang: "es", link: "/es/" },
  },
});
```

The selected language is carried by the URL (`/`, `/fr/`, `/es/`). Do not store a second
language preference for docs: the URL is the source of truth.

## GitHub wiki

GitHub Wikis have no native locale switcher. Do **not** maintain three full copies of every wiki
page with suffixes (`Page-fr`, `Page-es`): links, search, and sidebars drift immediately.

Until the docs site is published:

- Keep the wiki in English.
- Add a language notice at the top of the wiki home that links to the docs site once available.
- Treat the wiki as an onboarding mirror, not a second translation surface.
- When the docs site goes live, make the wiki home link to it and stop adding new wiki-only
  content.

## Contributor checklist

When you change documentation:

1. Update the English source page.
2. Update the French and Spanish pages in the same change when the localized tree exists.
3. Keep headings, links, and code samples aligned across languages.
4. Run the docs build or link check if the repository provides one.
5. Mention any page intentionally left untranslated in the pull request.

Run the site with `make docs-install` then `make docs-dev`. Build with `make docs-build`. For a
GitHub Pages project site, build with `DOCS_BASE=/saas-ui/ make docs-build`.

## Why not translate the wiki first

A wiki page selector is cosmetic without translated pages, and suffix pages are expensive to keep
in sync. A small static docs site gives one selector, one sidebar per language, clean URLs, and a
single build check. That is the durable path for a project with three supported languages.
